================================================================================
步骤 1.5：重跑增强分析（推荐，尤其代码改动后）
================================================================================

  这个步骤会用当前最新代码重跑 crash pipeline（不重新 fuzz），
  更新 crash_analysis.yaml 中的 triage / location / dedup / timings 等字段
  你已经修改过 `debugger.py` 和 `run_fuzzer.py`，建议执行此步骤

对每个项目执行：

python fuzzing.py \
  --yaml /home/cc/CKGFuzzer-1/fuzzing_llm_engine/external_database/c-ares/config.yaml \
  --reanalyze \
  --skip_gen_driver --skip_summary_api --skip_check_compilation --skip_gen_input

  （cJSON、curl 同理，替换对应 config.yaml 路径）

说明：
  - 不重跑 fuzz，只重跑已有 crash 的增强分析流程
  - 会刷新 Stage4/Stage6 相关实验字段（例如 timings）
  - 比完整 fuzz 快很多，但会有一定 LLM 调用开销

================================================================================
步骤 2：追溯修复 — 修复 repro_rate 和 GDB 运行时上下文（历史数据强烈建议）
================================================================================

  *** 对历史数据：强烈建议在消融实验之前执行！***
  *** 对新跑数据：可选（用于补齐/校正运行时上下文）***
  消融实验的 V3/V4 需要 GDB 运行时上下文作为 LLM prompt 输入。
  如果不先修复 GDB 数据，V3/V4 的 LLM 分析中将没有运行时上下文，
  导致无法验证 "runtime context breaks LLM hallucination" 的论点。

所有项目 fuzz 完成后，统一执行追溯修复脚本：

  # 先预览（不修改文件）
python -m crash.retro_enrich --db-root external_database --dry-run
 （或者对单个项目预览）
python -m crash.retro_enrich --db-root external_database --project libpcap --dry-run

  # 【推荐】带 ASan 重编译 + 追溯修复（一条命令搞定）
  # 由于 fuzz 流程最后一步是 coverage 编译，/out/ 里的 binary 没有 ASan，
  # 导致 PoC 无法复现。--rebuild-asan 会自动重编译后再做 GDB 追溯。
python -m crash.retro_enrich --db-root external_database --rebuild-asan

  # 或只处理单个项目####################################################################################
python -m crash.retro_enrich --db-root external_database --project zlib --rebuild-asan

  # 如果已确认 /out/ 里是 ASan binary（不需要重编译），可省略 --rebuild-asan：
python -m crash.retro_enrich --db-root external_database

说明：
  此脚本修复两个已知问题（不重跑 LLM，保留所有已有分析结果）：
  (a) repro_rate 0/3 → 在 Docker 容器内重新复现 PoC，使用多级签名比较
      原 bug：签名比较只用 primary signature（dedup:xxx vs sig:xxx 格式不同）
      修复：依次比较 exact → stack → fuzzy 三级签名
  (b) GDB crash_frame 为空 → 在 Docker 容器内运行 GDB（而非 host 上）
      原 bug：host 环境与容器不同，ASan 行为不一致，GDB 无法解析符号
      修复：在 Docker 容器内安装 GDB 并运行，确保环境一致
  (c) /out/ 中 binary 是 coverage 版本 → --rebuild-asan 自动用 ASan 重编译
      原因：fuzz 流程最后一步 build_fuzzers --sanitizer coverage 覆盖了 binary
      修复：在追溯前用 build_fuzzer_file 重编译 ASan 版本
  修复后的 GDB 数据写入 crash_analysis.yaml 的 gdb_runtime_context 字段
  备份文件保存为 crash_analysis.yaml.bak.{timestamp}

实验总体流程图：
================================================================================

  场景A（新项目）:
  步骤1: Fuzzing 运行（所有项目）
    → 发现 crash → 解析 sanitizer → 规则 triage → 定位 → 去重
    → PoC 复现 → LLM 分析 → 保存 crash_analysis.yaml
    → 覆盖率插桩编译 → 跑 corpus 收集覆盖率 → 进入下一轮迭代

  场景B（已有历史数据，例如现有 c-ares/cJSON）:
  跳过步骤1（不重跑 fuzz）

  步骤2: 追溯修复（历史数据强烈建议）
    → 修复 PoC 复现率（Docker 内复现 + 多级签名比较）
    → 修复 GDB 运行时上下文（Docker 内运行 GDB）
    → 写入 gdb_runtime_context 到 crash_analysis.yaml

  步骤2.5: 重跑增强分析
    → 使用最新代码重跑已有 crash 的增强 pipeline
    → 更新 triage/location/dedup/timings 等字段

  步骤3: 消融实验（读取步骤2修复的 GDB 数据）
    → 对已有 crash 重跑 V0-V4 五种 LLM 配置
    → V3/V4 的 LLM prompt 中包含真实的运行时上下文

  步骤4-6: 数据分析
    → 生成 CSV → 人工标注 → 计算指标 → 填入论文
