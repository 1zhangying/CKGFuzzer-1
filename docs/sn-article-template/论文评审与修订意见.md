# 《Evidence-Guided Crash Adjudication for LLM-assisted Fuzzing of Third-party Open-source Libraries in Connected Vehicles》评审与修订意见

评审对象：[sn-article(4).pdf](<./sn-article(4).pdf>)

评审方式：依据 `awesome-ai-research-writing` 技能的严格审稿流程，从研究贡献、方法严谨性、实验公平性、结论证据、可复现性和论文写作等方面进行评审。

# Part 1 [The Review Report]

## Summary

本文提出 CrashSage，用于判定 LLM 自动生成 fuzz driver 后产生的崩溃究竟源于目标组件，还是来自 driver 误用。系统由规则引导过滤、代表性崩溃选择、静态/运行时上下文重建和 LLM 分析组成。论文在 12 个开源库、1021 份崩溃报告上开展实验，并在其中 876 份二分类样本上报告 79.78% precision、100.00% recall 和 88.75% F1，同时将 LLM 调用次数从 876 次降至 57 次。

研究问题具有现实价值，系统流程也较完整。但是，目前最严重的问题不在语言表达，而在真值构建、消融实验公平性、重复崩溃聚类正确性和定位能力验证不足。现有结果尚不足以支撑论文关于“准确归因、根因定位和高效分析”的完整结论。

## Strengths

1. **问题定义具有实用价值。** 论文区分了“人工编写或审核的可信 harness”和“LLM 自动生成的不可信 driver”。这是 LLM-assisted fuzzing 中真实存在但容易被忽略的问题。

2. **系统架构清晰。** 规则过滤、去重、上下文重建和 LLM 判定的分层设计具有可审计性，比直接将原始 sanitizer 报告交给 LLM 更为合理。

3. **实验覆盖面相对较广。** 实验包含 12 个不同类型的 C/C++ 开源库，并同时考察模型选择、提示词设计和运行开销。

4. **工程效率提升明显。** LLM 调用次数从 876 次降至 57 次，说明预处理和重复报告压缩具有实际工程价值。

5. **论文整体结构较完整。** 方法、公式、算法、实验问题和案例分析均有覆盖，英文整体可读性较好。

## Weaknesses (Critical)

### 1. Ground truth 构建可能引入系统性偏差

这是当前最重要的阻断问题。

表 8 将 “not reproducible” 和 “lacks sufficient evidence” 直接归入 confirmed non-target。但这两种情况并不等价于“确定不是目标组件缺陷”：不可复现可能来自环境差异、非确定性行为或未初始化状态；证据不足应属于 unresolved，而不应直接作为负类。

与此同时，145 个 “potential unpublished API bug” 被完全排除出二分类指标。然而，新发现、没有公开 CVE 或补丁的崩溃恰恰是该系统最重要的应用对象。当前 100.00% recall 只针对具有公开证据的 146 个 target 报告，不能说明系统对未知漏洞也具有同等召回能力。

建议：

- 将标签体系改为 `confirmed target / confirmed driver-induced / out-of-scope / unresolved`。
- 不可复现和证据不足样本不得直接作为负类。
- 说明标注人员数量、专业背景、是否独立标注、分歧解决过程和一致性指标。
- 对每个 confirmed target 给出 CVE、issue 或 patch ID、受影响库版本和根因映射。
- 同时报告 report-level、unique-root-cause-level 和 library-level 指标。
- 对全部 1021 个样本报告三分类或四分类结果及 coverage–accuracy，而不只报告筛选后的 876 个样本。

### 2. V0–V1 对比无法证明改进来自规则过滤

表 7 中 V0 使用 “CKGFuzzer classifier”，而 V1 同时采用规则过滤和新的 differential prompt。因此，V0 到 V1 的变化同时混入了：

- 输入过滤变化；
- 提示词变化；
- 可能的输入证据格式变化。

但是，第 5.2 节将全部提升归因于 rule-guided attribution，当前因果结论不成立。

建议重新设计如下消融实验：

| 变体 | 配置 |
|---|---|
| B0 | raw report + 统一模型与统一提示词 |
| B1 | normalized report |
| B2 | B1 + rule filtering |
| B3 | B2 + representative selection |
| B4 | B3 + static context |
| B5 | B4 + runtime context |
| B6 | B5 + differential prompt |

除被考察模块外，模型、提示词、输入字段和解码参数必须保持一致。

### 3. “去重率”很高，但没有验证是否错误合并

代表性选择将 258 个报告压缩为 57 个，但论文只报告压缩率，没有评估聚类正确性。不同根因可能具有相同 bug type 和相似调用栈。一旦错误合并，代表性报告的诊断将传播给组内所有成员，从而掩盖独立漏洞。

方法本身也缺少若干关键细节：

- 式（4）中的前缀长度 \(k\) 没有给出具体值。
- frame key 究竟包含函数、文件、行号还是地址没有明确定义。
- exact signature 仅使用 \(H(d(c))\) 时，没有加入 library、version、binary 等命名空间。
- 代表性样本依赖 discovery order，但没有进行顺序敏感性分析。

建议人工建立 unique-root-cause 分组，报告 pairwise precision、recall、F1、B-cubed 指标，以及 over-merging 和 under-merging 数量，并分析不同 \(k\) 值和不同输入顺序下的结果。

### 4. 论文声称改善“根因定位”，但实验只评价二分类归因

CrashSage 的输出包括 root-cause type、location、trigger condition、severity 和 fix suggestion，但表 14–17 仅评价 target/non-target 分类。由此最多可以证明 attribution 得到改善，不能证明：

- 根因位置更加准确；
- 根因类型更加准确；
- 严重性判断可靠；
- 修复建议有效。

建议增加函数级、文件级和语句级定位准确率、Top-k localization accuracy，并由独立专家盲评根因解释和修复建议的正确性。

### 5. 规则阈值缺少独立调参与泛化验证

\(h_D=3\)、\(\theta_D=0.8\)、\(m_P=2\)、\(\theta_S=10\) 目前主要由经验和直觉解释。论文声称这些参数在评估前固定，但没有说明参数是在何种数据上确定的，也没有提供敏感性实验。

此外，R6、R7 和 R10 可能把“由 driver 输入触发、但目标组件没有正确检查参数”的真实组件缺陷过滤掉。规则优先级又是 noise → likely driver bug → target crash → needs review，因此同时匹配多条规则的报告可能优先被删除。

建议增加：

- 每条规则的匹配数和独占匹配数；
- 规则之间的重叠与冲突矩阵；
- 阈值敏感性分析；
- leave-one-library-out 验证；
- 独立开发集与测试集；
- 被过滤样本的人工抽查和置信区间。

### 6. 将 timeout、OOM 和 LSan 报告统一称为 noise 不准确

在联网汽车或安全软件场景中，资源耗尽、超时和内存泄漏可能构成拒绝服务或长期可靠性问题。它们可以超出本文“memory-safety crash attribution”的研究范围，但不应被表述为没有价值的噪声。

建议将该类别改称 `out-of-scope condition`，单独统计并保留相关记录，同时缩小论文的任务定义。

### 7. Case 3 暴露了归因标准上的潜在矛盾

第 5.6 节称 driver 直接设置 `pb->bpos` 接近 `INT_MAX`、保持 `pb->size` 很小，然后调用 `printbuf_memappend`，最终将其判为 API bug。这个操作表面上很像 driver 主动构造不一致的内部状态，与论文定义的 driver misuse 高度相似。

作者必须说明：

- 这些字段是否属于允许调用者修改的公开 API；
- 对应的 API contract 是什么；
- 为什么该输入不属于非法对象状态；
- 对应的公开 issue、CVE 或 patch 是什么；
- 目标组件应承担参数检查责任的依据是什么。

如果无法建立明确的契约证据，该案例应重新标注。

### 8. “Connected Vehicles” 场景支撑不足

12 个实验对象本身是通用开源库。表 6 只是给出了 “Gateway DNS”“OTA/log compression”等可能的部署角色，但没有真实车载软件栈、车载配置、实际依赖关系或车辆环境实验。当前方法和实验本质上适用于一般的 LLM-assisted library fuzzing。

可以选择两种修改方向：

- 增加真实车载项目依赖、软件版本、调用路径和威胁模型；
- 或删除标题中的 “in Connected Vehicles”，将联网汽车作为潜在应用场景，而不是核心实验场景。

### 9. 可复现性信息不足

论文尚缺少：

- 12 个库的具体版本和 commit；
- fuzz driver 数量、生成提示和编译参数；
- 每个 fuzz target 的运行时间、初始种子和停止条件；
- ASan、UBSan、LLVM、libFuzzer 和 GDB 版本；
- 完整规则实现和最终提示词；
- LLM 的具体模型快照、调用日期、API 参数和重复运行结果；
- replay 成功、失败、mismatch 和 GDB 不可用的具体数量；
- 总 API 成本、端到端时延以及 P50/P95 时延。

尤其需要注意的是：表 12 同时写规则作用于 1021 个报告、代表性选择作用于 258 个报告、上下文重建作用于 57 个报告，但 258 和 57 来自 876 个 binary-evaluable 样本。145 个 unresolved 报告在实际流水线中的去向并不清楚。

## Rating

- **综合评分：4/10**
- **审稿建议：Major Revision；若按顶级软件工程或安全会议标准，则为 Weak Reject**
- **审稿信心：4/5**

论文具有明确的工程价值和较高的可救性，但当前实验设计不足以证明核心性能提升分别来自所提出的各个模块。

# Part 2 [Strategic Advice]

## 问题根源

论文目前呈现的是“完整系统加漂亮的报告级指标”，但缺少能够说服审稿人的独立证据链：

1. 真值是否可靠；
2. 规则是否能够在独立数据上泛化；
3. 去重是否没有错误合并不同根因；
4. 上下文是否真的改善根因定位；
5. 指标是否被大量重复报告放大。

因此，继续润色英文不能解决主要风险，必须优先重构实验。

## 可救性判断

可救性较高。系统框架、数据和实现似乎已经具备，主要工作是重新组织真值、补充公平消融、验证聚类正确性并收缩缺乏充分证据的结论。

如果无法获得 unique-root-cause 标注和 API contract 证据，则应将论文定位从“自动准确判定漏洞归属”降低为“evidence preparation and prioritization aid”。

## 行动指南

### P0：投稿前必须完成

1. 重建四类真值体系，将“不可复现/证据不足”移出负类。
2. 对全部 1021 个报告交代处理结果，并增加根因级指标。
3. 使用同一模型、同一提示词重做逐模块消融。
4. 评价代表性选择的聚类准确率，而不只报告压缩率。
5. 单独评价静态上下文和运行时上下文。
6. 审核 json-c Case 3 的 API contract 与标签。
7. 补充每个 confirmed target 的公开证据映射。

### P1：显著提高录用概率

1. 加入 sanitizer token、简单 stack hash、已有 stack-trace clustering 方法等公平基线。
2. 增加 leave-one-library-out、阈值敏感性和 bootstrap 置信区间。
3. 增加根因位置、根因类型和修复建议评价。
4. 报告 replay 成功率及缺失 runtime evidence 时的性能。
5. 解释为何主结果选择 Qwen3-Coder-Plus，而不是 F1 更高的 Qwen3.7-Max。
6. 增加标准的 Threats to Validity 小节，分别讨论内部、构念和外部有效性。

### P2：文字与格式修正

- 第 11、20 页的 `likely api bug` 应统一为 `target crash`，或重新明确定义该标签。
- 引言结尾应写明 “Section 6 discusses limitations, and Section 7 concludes the paper.”
- 第 16 页 “Table 3 lists the 13 rules” 位置错误，应移至规则表附近或删除。
- 明确定义 \(k\)、frame key 和 stable hash。
- 式（8）应增加括号，避免逻辑优先级歧义。
- 图 3、图 4 的横轴标签和柱顶文字过小，建议放大字体或改为更简洁的表格。
- 摘要应明确结果来自 “876-report binary-evaluable subset at report level”，并说明另有 145 个 unresolved reports 未计入二分类指标。
- 如果不补充真实车载环境验证，建议将标题改为：

  > Evidence-Guided Crash Adjudication for LLM-Generated Fuzz Drivers

## 建议的论文修改顺序

1. 首先重构 ground truth 和数据统计。
2. 然后完成公平消融、聚类验证和定位评价。
3. 根据新实验结果重新撰写摘要、贡献和结论。
4. 最后统一术语、修正公式与交叉引用，并进行英文润色。

只有在前三项完成后，摘要中的 precision、recall、F1 和 93.49% reduction 才具有足够可信的解释基础。
